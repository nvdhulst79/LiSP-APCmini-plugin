# LiSP × APC Mini mk2 Plugin

Linux Show Player plugin giving plug-and-play APC Mini mk2 integration with the **Cart Layout**: pad press fires the cart at that grid position, pad LED reflects cue state. Zero per-cue MIDI configuration.

Full context: [documentation/primer.md](documentation/primer.md) — read this for goals, rejected alternatives, MIDI reference, proposed plugin layout, and rationale.

## Stack

- **Host:** Linux Show Player (LiSP), tracking the **`develop` branch** — Python ≥3.10 / PyQt5 / GStreamer. (Not `master` and not the v0.6.5 tag — `develop` is the only branch where pyliblo3 has been replaced with pure-Python `python-osc` via [PR #338](https://github.com/FrancescoCeruti/linux-show-player/pull/338), which is needed to build on Ubuntu 24+/Debian 13.)
- **Plugin source (canonical):** the **repo root** of this project — the repository *is* the `apc_mini_cart` plugin package (`__init__.py`, `apc_mini_cart.py`, `constants.py`, `settings.py`, `default.json` all live at the root). **Do not** edit files in LiSP's tree directly. (The code used to live in an `apc_mini_cart/` subdir; it was hoisted to the root on 2026-05-21 to make this a standard public plugin repo.)
- **LiSP integration:** symlinked into the from-source install at `~/dev/linux-show-player/lisp/plugins/apc_mini_cart` → `<this project>` (the repo root). LiSP only scans `lisp/plugins/` at startup, so restart LiSP after adding/removing the symlink (editing inside the symlinked folder while LiSP runs is fine — LiSP doesn't hot-reload plugins anyway).
- **Symlink command** (run once):

- **Hardware:** Akai APC Mini mk2 (8×8 grid, MIDI Note 0–63 on Ch 0)

## Project status

Currently in **v1 feature-complete** phase. Inbound MIDI, LED feedback (solid + pulse/blink), one-shot installer, app-level settings page, per-cue idle-color override, and identify-button smoke test are all in place (2026-05-20). Settings UI is *minimal-cut* — other proposed UI affordances are listed under "Deferred Step 7 scope" below. Deployment script still not exercised on a clean show-machine target.

> **MIDI port gotcha:** the APC mini mk2 exposes *two* MIDI ports — `APC mini mk2 Control` and `APC mini mk2 Notes`. The plugin requires **Control**. In LiSP, set it under `Preferences → MIDI → Input/Output device`. With "Notes" selected, pads send chromatic-keyboard MIDI on different channels/notes and the plugin sees nothing on Ch 0 notes 0–63.

**Bugfix — running color silently turned white (2026-05-21).** Symptom: the running-state color kept reverting to white (looked tied to config-version bumps). Root cause was *not* version migration — it was a palette/default mismatch. `DEFAULT_COLORS["running"]` (and `default.json`) use bright green `87`, but the settings combo's `PALETTE_CHOICES` only offered green `21`. On opening Preferences, `loadSettings → _select_combo_value(runningCombo, 87)` calls `QComboBox.findData(87)` → `-1` → falls back to index 0 (White); `getSettings` then writes White back. The version correlation was a red herring: a version bump wholesale-copies `default.json` (running=87, green) over the user config — LiSP's `JSONFileConfiguration._check_file` does a `copyfile`, not a merge — so the grid is green again until the settings page is next opened and re-saves White. Fix: point the palette's "Green" at `87` (one green, matches the default) and harden `_select_combo_value` to log a warning instead of silently coercing. **Invariant going forward:** every value in `DEFAULT_COLORS` must appear in `PALETTE_CHOICES`. Already-affected configs self-heal on the next `_version_` bump (now at 0.6, so the next launch resets to defaults and restores green).

**Phase 2 — Fader mappings, code-only (2026-05-21).** Implements the row-select + soft-takeover + pan-mode design from [documentation/phase2-faders.md](documentation/phase2-faders.md). `_on_midi_message` is now a dispatcher: grid notes 0x00–0x3F → existing cue trigger (extracted into `_handle_grid_press`); Scene Launch notes 0x70–0x77 → `_handle_scene_press`; Shift note 0x7A → tracked via `_shift_held` (note_on sets, note_off clears, mido auto-converts vel-0 note_on to note_off); fader CCs 0x30–0x37 → `_handle_fader`; master fader CC 0x38 intentionally ignored. Scene-press logic: plain tap selects the row in volume mode, plain tap of a selected volume-mode row deselects, plain tap of a selected pan-mode row reverts to volume, Shift-tap on selected toggles volume↔pan, Shift-tap on any other row selects it directly in pan mode. Scene Launch LEDs (`90 NN VV`, VV=0/1/2 for off/on/blink) signal selection. **Keylight (2026-05-21):** by default every row button is lit *dim* (channel nibble 1 = 25%) so it's findable in the dark, the selected volume-mode row is *bright* (nibble 6 = 100%), pan-mode selected *blinks*. This assumes scene buttons honor the brightness nibble like pads do — **unverified**; the `scene_keylight` config flag (app-level checkbox, default on) falls back to the original off/solid/blink (channel 0 only) if the hardware ignores it. `_scene_led_params(row, keylight)` returns the `(channel, velocity)` pair; `_send_scene_led` now takes both. `_activate` paints scene LEDs (was clearing them); `_on_config_changed` repaints them so the toggle takes effect live. The **Shift button has no addressable LED** on the mk2 — it can't be lit, so pan arming shows only via the row blink. `default.json` → `_version_` `0.6` (adds `scene_keylight`). **Soft takeover:** per-column `_slider_latched[8]` + `_slider_position[8]` (−1 = unknown until first CC after arm); latch fires when `(prev_cc − target_cc) * (curr_cc − target_cc) <= 0` — i.e. the slider has crossed or landed on the target value in CC space. Latches reset on row change, mode change, page change, and model change (via `_invalidate_page_bindings`). **Property access:** `cue.media.element("Volume")` / `cue.media.element("AudioPan")`; we ride `live_volume` (the runtime knob, not the baseline `volume`) and `pan`. Non-MediaCues, and MediaCues missing the requested element, leave the slider inert — no error, no LED change. **Pipeline gotcha (now surfaced):** the default GStreamer pipeline in LiSP is `["Volume", "Equalizer10", "DbMeter", "AutoSink"]` — **AudioPan is not in it**, so pan is unavailable on every cue until the user adds it (Preferences → GStreamer applies to *new* cues only; existing cues need it per-cue in media settings). Volume *is* in the default pipeline so volume mode works out of the box. Surfaced 2026-05-21: `_warn_if_pan_unavailable` logs a `WARNING` (→ status bar + log-viewer count) when a row freshly enters pan mode and `_row_has_pan` finds no `AudioPan` element in any of its cues. Fires only on entry into pan mode, not per scene press. **Mappings:** volume CC 0..127 → 0.0..1.0 (unity at top; for >unity the operator sets the cue's baseline higher and rides it down); pan CC 0..127 → −1.0..+1.0 with ±1 CC center detent at 64 so near-center snaps cleanly to 0.0. **Phase 2 — hardware-test fixes (2026-05-21, second pass).** First on-hardware test of the fader work surfaced three issues; all fixed. `default.json` → `_version_` `0.7`. (1) **Volume reset on replay.** Symptom: a fader-set volume held for one playback, then the cue replayed at its configured volume; pan was unaffected. Root cause: we rode `live_volume`, a runtime-only `GstLiveProperty` that `Volume.stop()` resets to the baseline `volume` on every stop ([elements/volume.py](../linux-show-player/lisp/plugins/gst_backend/elements/volume.py) `stop()` → `self.live_volume = self.volume`) and that is never serialized. `pan` is a plain serialized `GstProperty` with no such reset — hence the asymmetry. Fix: `_write_property`/`_read_property` now use the **baseline `volume`** property in volume mode. This persists across replays, saves into the session, is still heard live (same `set_property` on the gst element), and — bonus — the **Cart widget's volume slider now follows the fader**, because that slider repaints from `changed("volume")` (the baseline signal), not from `live_volume`. The APC fader is *linear* in amplitude (CC 0..127 → 0.0..1.0) while the Cart slider rides a dB/fader curve, so the two won't show the same position — cosmetic, unchanged. (2) **Cart volume slider doesn't take mouse input.** Not our bug: the Cart widget enables that slider only while the cue is `Running` ([cue_widget.py:213](../linux-show-player/lisp/plugins/cart_layout/cue_widget.py#L213)) and only shows it when "Show volume" is on in the layout menu — built-in LiSP behavior, left as-is. (3) **Scene Launch buttons can't dim.** Confirmed: the brightness nibble is ignored. Removed the whole keylight feature — the `scene_keylight` config key (gone from `default.json`), its app-settings checkbox + hint, `SCENE_DIM_CHANNEL`/`SCENE_BRIGHT_CHANNEL`, and the `(channel, velocity)` plumbing. Scene LEDs are state-only again: unselected = off, selected-volume = solid on, selected-pan = blink (`_scene_led_state(row)`, channel 0). Trade-off accepted: unselected rows are dark, so row buttons aren't findable in a blackout — hardware leaves no alternative. (4) **Shift is unusable.** On hardware, `Shift +` some Scene Launch buttons fires built-in firmware modes (e.g. a demo mode), so Shift can't be repurposed. Dropped `_shift_held`, `APC_SHIFT_NOTE`, and the note_off branch. Pan is now reached by a **three-state cycle**: each tap of a row's Scene Launch button goes volume → pan → off; tapping a *different* row jumps to it in volume mode. `_handle_scene_press` rewritten accordingly.

**Step 7c — Pad-press trigger mode (2026-05-20).** Replaces the previous `cue.execute()` dispatch with a configurable mode. Two modes: `toggle` (LiSP's native — `cue.execute()`, press again to stop) and `retrigger` (interrupt + start, always plays from the beginning). Global default switched to `retrigger` per user request — that's what most operators expect from a clip-launcher grid, and the LiSP-native toggle was surprising in a show context. Plumbing: new app-level combo "Pad press behavior → Default action"; new per-cue combo "Pad action: [Default | Retrigger | Toggle]"; new `Cue.apc_trigger_mode = Property(default=None)` (None = use global). Dispatch in `_on_midi_message` calls `_trigger_mode_for(cue)` which prefers the per-cue value over `Config["trigger_mode"]` over the `TRIGGER_MODE_DEFAULT` constant. `default.json` bumped to `_version_` `0.4`. **Important gotcha:** the obvious `cue.interrupt(); cue.start()` does NOT work — both `Cue.interrupt` and `Cue.start` are decorated with `@async_function` (each spawns its own thread and returns immediately), so calling them back-to-back races on `_st_lock`. `start()` typically wins, observes `_state & IsRunning` is still True (interrupt hasn't run), and silently returns; then interrupt stops the cue, with no restart. Symptom: cue stops on the second press as if nothing happened. Fix lives in `_retrigger()`: spawn one thread that calls `cls.interrupt.__wrapped__(cue)` then `cls.start.__wrapped__(cue)` — the `__wrapped__` attribute is set by `functools.wraps` inside the `@async_function` decorator and gives access to the original sync body. This serializes interrupt-before-start on a single thread. Verified `Cue.interrupt.__wrapped__` resolves correctly in the LiSP venv.

**Step 7b — Brightness controls (2026-05-20).** Follow-up addition to the app-level page: two horizontal `QSlider`s (idle and running) with tick marks at every notch and a live percent label to the right. Slider range is 0–6, mapping 1:1 to the APC's solid-brightness behavior nibbles (10%/25%/50%/65%/75%/90%/100%) — discrete steps with `setTickInterval(1)` so the slider snaps to valid hardware values rather than implying continuous brightness the device can't deliver. Paused (pulse) and error (blink) deliberately *not* exposed — those behavior nibbles bundle animation pattern with fixed firmware brightness; there's no orthogonal dim knob. UI carries an inline hint to that effect. `_led_for_cue` reads `Config["brightness.idle"]` / `Config["brightness.running"]` instead of the hardcoded `BEHAVIOR_DIM` / `BEHAVIOR_FULL` constants (constants kept for `identify()` and `LED_OFF`). `default.json` bumped to `_version_` `0.3` adding the `brightness` block. Initial combo-box implementation was swapped for sliders on user request — both work, sliders feel more natural for a brightness knob and the snap-to-tick keeps them honest.

## Key technical reference (cheat sheet)

Full MIDI table in the primer. The two things you'll reach for most:

**Grid coordinate conversion** (APC note 0 = bottom-left; Cart (0,0) = top-left):
```
cart_row = 7 - (note // 8)
cart_col = note % 8
note     = (7 - cart_row) * 8 + cart_col
```

**LED control:** Note-On `9X NN VV` — `X` = behavior (0–6 solid brightness, 7–10 pulse, 11–15 blink), `NN` = pad note 0x00–0x3F, `VV` = color from 128-entry palette (0=off, 5=red, 13=yellow, 21=green, 45=blue, 87=bright green).
